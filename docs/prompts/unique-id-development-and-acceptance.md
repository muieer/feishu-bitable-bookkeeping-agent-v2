# unique_id 核对、单次补写与独立验收任务提示词

以下保存本次开发任务的原始提示词，包含开发要求、交接报告、独立验收和验收结果处理要求。

---

请在当前项目中完成下面的开发任务，并在开发完成后，在当前聊天中创建独立验收子智能体进行验收。阶段之间无需再次向我确认。

先阅读并遵守项目的 `AGENTS.md`。本次工作包含开发和独立验收两个阶段，两者通过开发完成后的交接报告衔接。

**一、开发目标与业务要求**

目标多维表格中已经新增文本字段 `unique_id`，用于记录程序写入的唯一 ID。

请实现以下流程：

**写入结果不确定 → 等待 3 秒 → 按 `unique_id` 查询一次 → 查到则确认成功，查询成功但查不到则补写一次。**

具体业务要求：

1. 每笔消费由程序生成一个 UUIDv4，写入现有 `unique_id` 字段。原始写入、查询和补写始终复用同一个 ID，模型不负责生成或填写 ID。
2. 首次远端写入前，复用现有 SQLite 执行日志，持久保存 ID 和已经校验通过的消费数据。补写使用保存的数据，不重新调用模型，不重新计算日期或分类。同一笔消费重复进入工具时，复用已有提交记录，不能重新启动补写流程。
3. 明确成功的写入直接返回成功，明确失败的写入沿用现有失败处理。只有提交后结果不确定时，先保存待核对状态，再异步等待 3 秒，然后按 `unique_id` 精确查询一次。使用现有 CLI、指定账本和现有身份。
4. 根据查询结果处理：
   - 查到唯一一条记录，且业务内容与本地保存的数据一致：保存飞书记录 ID，更新为成功，不补写。
   - 查询成功、结果完整且没有记录：复用原 ID 和原始数据，补写一次。
   - 查询失败、超时、响应无法解析、内容冲突或查到多条相同 ID：保留待核对，不补写。
   - 补写明确成功：更新为成功。
   - 补写未能确认成功：保留待核对。即使补写被明确拒绝，也不能据此认定第一次提交失败。
   - 不再进行第二轮等待、查询或补写。
5. 保持实现简单。将处理放在写入工具或账本执行层内部，不放到 Harness 收尾阶段，不增加模型工具、后台轮询、消息队列或新的存储系统。保留现有取消和进程中断处理，不增加重启后的自动补写。补发卡片不能触发写入，最终报告和卡片应反映持久保存的实际结果。
6. 兼容现有 SQLite 数据库。旧记录如果没有写入 ID，保留原有处理方式，不能补造 ID 后自动重写。启动检查应验证现有 `unique_id` 字段存在且为文本类型；不自动修改真实表结构。

本方案接受原请求延迟完成、可能与补写形成重复记录的边界，不要求实现严格幂等。不要为消除这个已接受的边界扩展系统复杂度。

其余业务行为遵循项目原有规格。自行选择必要的开发测试与检查，完成与改动相称的验证。测试使用人工合成资料，全程离线，不调用真实模型、不连接飞书、不向真实表格或会话写入测试数据。

**二、开发完成后，形成验收交接报告**

完成实现和开发自测后，先整理一份面向未参与开发者的交接报告，作为独立验收的输入。

交接报告应自包含，说明：

- 原始业务目标，以及本次实际交付的行为。
- 关键实现思路、主要改动位置和必要的兼容处理。
- 已完成验证的范围与结果。
- 已知限制、尚未验证的事项，以及对原需求的任何偏离；没有偏离则明确说明。

报告应描述实际完成的实现，不只复述计划。提供验收所需的定位信息，但不要替验收者设计测试用例或规定预期结论。

**三、在当前开发聊天中启动独立验收**

使用当前聊天的子智能体能力，创建一个独立验收子智能体，不另建用户聊天。

让验收子智能体使用独立上下文，不直接继承完整开发对话。显式向它提供：

- 项目目录和项目规则的读取要求。
- 本提示词第一部分的完整业务要求。
- 开发完成后的交接报告。
- 下面第四部分的完整验收任务。

子智能体应直接检查当前实际代码。原始业务要求是判断标准，开发报告用于理解和定位实现，不能把开发者的交付声明直接视为事实。

如果当前环境无法创建子智能体，应如实说明，不得将主智能体自行检查描述成独立验收。

**四、交给验收子智能体的任务**

你的角色是独立验收者。你没有参与开发，请根据收到的原始业务要求、开发交接报告和当前项目，自行设计并执行验收，最后提交结果报告。

你的验收范围是从消费原文输入到最终结果报告生成的完整记账业务流程，重点检查本次改动及其对原有行为的影响。

请遵循以下原则：

1. **独立设计。**\
   自行理解业务目标，选择有代表性的业务场景，构造数据，推导预期结果，决定验证方式。具体场景和用例由你设计，不受开发者测试方案约束，也不预设固定用例数量。
2. **依据业务判断。**\
   预期结果应来自原始要求和业务规格，不能仅根据当前实现反推正确行为，也不能调用待验收的同一套判断逻辑生成“正确答案”。开发报告帮助理解实现，但其中的声明需要验证。
3. **允许要求重叠，保持证据独立。**\
   可以阅读已有代码和测试，理解接口及开发者已经验证的内容。允许验证相同业务要求，但不能复制旧用例后改名、替换少量数据，不能直接复用旧测试的业务预期或响应脚本，也不能仅重跑原有测试就宣布验收通过。
4. **验证实际执行链路。**\
   以完整业务流程的验证为主，必要时补充专项检查。尽量让实际生产代码参与运行，将模拟放在模型、飞书和通知等外部边界，不能替换掉待验收的核心逻辑。模拟账本应维护独立状态，不得擅自提供真实目标不具备的唯一约束或原子性。
5. **完全离线。**\
   不调用真实模型、不连接飞书、不发送真实消息。使用人工合成的配置、知识库和消费数据，不读取真实凭证或生产运行数据库。自行选择可控时间和故障注入方式，但不能为了方便测试修改生产逻辑。
6. **保留可复现证据。**\
   每项验收应能说明验证了什么业务要求、为何预期该结果、实际发生了什么，以及证据在哪里。发现失败时，先检查测试自身和模拟边界是否正确，再确认是否属于实现问题。
7. **保持验收职责独立。**\
   可以新增独立验收测试和报告，不修改业务源码、原有测试或生产配置。发现问题后提供复现证据，由开发智能体负责修复。对已明确接受的方案边界，不擅自增加更强要求。

验收完成后，提交自包含的报告，说明：

- 验收对象、范围与结论。
- 场景选择思路，以及相对开发测试的独立性。
- 实际执行的验收项目、结果与证据。
- 发现的问题、业务影响、复现方式和必要的代码定位。
- 测试与报告的保存位置及复现命令。
- 未覆盖、无法验证或证据不足的部分。

能够判断时，区分本次改动引入的问题和既有问题；不能判断时如实说明。分别交代本次功能是否满足要求，以及完整业务流程是否发现其他问题。

离线模拟不能证明真实模型的理解准确率、真实飞书接口表现或真实卡片送达能力，报告中应明确这一结论边界。

请实际完成设计和执行，不要只返回验收计划。

**五、处理验收结果并完成交付**

主开发智能体等待验收结果，审查其证据和结论。

对确认与本次改动相关的缺陷，完成修复和必要自测，更新交接说明，再交给同一验收子智能体独立复验。不要通过放宽业务要求、删除失败用例或修改验收预期来获得通过结论。既有且与本次改动无关的问题应记录，不自行扩大开发范围。

最终向我汇总：

- 实际完成的功能和关键实现思路。
- 开发自测结果。
- 独立验收结论及报告位置。
- 验收发现的问题及处理结果。
- 剩余限制或尚未完成的事项。

只有取得相应验收证据后，才能声明验收通过；无法完成的部分应明确说明原因。
